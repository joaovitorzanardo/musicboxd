# MBD-20 Logout Revokes the Session's Refresh Token — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `DELETE /api/v1/auth/refresh` revokes the session behind the caller's refresh cookie, so that token (and any token rotated from it) can never mint another access token. A fresh login still works.

**Architecture:** MBD-19 already models a session as a refresh-token *family* with a `revoked_at` column, and `rotate` already rejects any token whose family is revoked. Logout is therefore one new service method, `RefreshTokenService.revoke(raw)`, that takes the same locks in the same order as a rotation (token row, then family row) and sets `revoked_at`. The controller exposes it on the refresh cookie's own path, answers `204` and clears the cookie.

**Tech Stack:** Java 25, Spring Boot 4.1.1 (Spring Security 7, OAuth2 resource server), Spring JDBC `JdbcClient`, PostgreSQL 18, JUnit 5 / MockMvc / AssertJ / Hamcrest, Testcontainers.

## Decisions (defaults chosen for this story)

| Question | Decision |
|---|---|
| Route | `DELETE /api/v1/auth/refresh` (decided in MBD-19: the cookie is scoped to that path, so the browser sends it there and nowhere else). |
| What is revoked | The **whole family** (that login/device). A token-only revoke would leave grace-window siblings alive. Other devices stay logged in. |
| Authentication | **None besides the cookie.** No bearer token required: the person must be able to log out after the 15-min access token expired. The bearer header is ignored on this path (already true: `PUBLIC_AUTH_PATHS` matches by path, any method). |
| Response | Always `204 No Content` plus `Set-Cookie: musicboxd_refresh=; Max-Age=0`, also for a missing, unknown, expired or already-revoked cookie. Logout is idempotent and reveals nothing. |
| CSRF | Stays disabled. A cross-site `DELETE` needs a CORS preflight the API never grants, and `SameSite=Lax` keeps the cookie off cross-site non-GET requests. Worst case of a forged logout is a logout. |
| The access token after logout | Stays valid until it expires (≤ 15 min, stateless JWT, AD-8). The SPA drops it from memory (MBD-22). No deny-list. |
| "Log out everywhere" | Out of scope. |
| Rate limit | None (MBD-23 owns limits; logout creates nothing). |

## Global Constraints

- Only `SHA-256(raw)` is ever looked up or stored; the raw token never appears in a body or log line. Log the account id and family id only.
- Revocation is `refresh_token_families.revoked_at`. No schema change, no migration, no new config, no deploy change.
- Lock order for every write on a family: the token row (`findForUpdate`) first, then the family row (`lockFamilyAndCheckRevoked`). Never the other way round (deadlock).
- After logout, the old token on `POST /api/v1/auth/refresh` gets the existing 401 Problem Details, `type` `urn:musicboxd:problem:invalid-refresh-token`.
- Routes under `/api/v1`, documented by springdoc (AD-7). Java sources use tabs. Repositories stay package-private.
- Out of scope: SPA logout button (MBD-22), access-token deny-list, logout-all-devices.

## Review Focus

- **Revoked, not merely expired-looking** (the story's high-risk note). Clearing the cookie proves nothing: the server must reject the old raw token when it is replayed by hand, and the family row must carry `revoked_at` while `expires_at` is still in the future. (Task 2: `logoutRevokesTheTokenServerSideNotJustTheCookie`.)
- **A refresh in flight when the person clicks logout.** Another tab's rotation may be inserting a successor at that moment; the successor must die too. (Task 1: `logoutAlsoKillsASuccessorThatIsBeingIssuedConcurrently`.)
- **Grace-window siblings.** Two tabs refreshed the same token within 10 s, each holding a different successor; logging out from one must kill the other. (Task 1: `revokeKillsEveryTokenOfTheFamily`.)
- **Logging out with an expired access token, a stale bearer header, or no cookie at all.** Must be 204, never 401 or 500. (Task 2: `logoutNeedsNoAccessTokenAndIgnoresAStaleOne`, `logoutWithoutAValidCookieIsStill204`.)
- **Logout on one device logs out every device.** It must not. (Task 1: `revokeLeavesOtherSessionsAlone`.)

```java
	@Test
	void logoutAlsoKillsASuccessorThatIsBeingIssuedConcurrently() throws Exception {
		String current = refreshTokens.issue(newAccount());

		var rotated = new CountDownLatch(1);
		var commit = new CountDownLatch(1);
		try (var pool = Executors.newFixedThreadPool(2)) {
			// Another tab refreshes; its transaction holds the locks and has not committed yet.
			Future<String> successor = pool.submit(() -> new TransactionTemplate(transactions).execute(status -> {
				String next = refreshTokens.rotate(current).refreshToken();
				rotated.countDown();
				await(commit);
				return next;
			}));
			assertThat(rotated.await(10, SECONDS)).isTrue();
			// Meanwhile the person clicks logout in this tab, with the same cookie.
			Future<?> logout = pool.submit(() -> refreshTokens.revoke(current));
			Thread.sleep(500); // let the logout reach the database and block on the row lock
			commit.countDown();
			logout.get(10, SECONDS);

			String next = successor.get(10, SECONDS);
			assertThatThrownBy(() -> refreshTokens.rotate(next)).isInstanceOf(InvalidRefreshTokenException.class);
		}
	}
```

- [ ] **Step 3: Implement `revoke`**

In `RefreshTokenService.java`, add this method after `rotate` (before `insertSuccessor`):

```java
	/**
	 * Logout (MBD-20): revokes the token's whole family, so grace-window siblings and a successor that a
	 * parallel refresh is issuing right now die with it. Same lock order as {@link #rotate}. Unknown, expired
	 * and already-revoked tokens are a no-op: logout always succeeds and reveals nothing.
	 */
	@Transactional
	public void revoke(String rawToken) {
		tokens.findForUpdate(OpaqueTokens.hash(rawToken)).ifPresent(token -> {
			if (!tokens.lockFamilyAndCheckRevoked(token.familyId())) {
				tokens.revokeFamily(token.familyId(), clock.instant());
				log.info("Logout for account {}: revoked family {}", token.accountId(), token.familyId());
			}
		});
	}
```

Also update the class Javadoc to mention logout:

```java
/**
 * Opaque refresh tokens (MBD-19, AD-8): hashed at rest, rotated on every use, reuse revokes the login's family.
 * Logout revokes it too (MBD-20).
 */
```

```java
	/** Logout. The cookie is the credential, so it works after the access token expired; it always answers 204. */
	@DeleteMapping("/refresh")
	@ApiResponse(responseCode = "204",
			description = "This session's refresh token is revoked (if there was one) and the cookie is cleared")
	public ResponseEntity<Void> logout(
			@CookieValue(name = RefreshCookies.NAME, required = false) String refreshToken) {
		if (refreshToken != null && !refreshToken.isBlank()) {
			refreshTokens.revoke(refreshToken);
		}
		return ResponseEntity.noContent().header(HttpHeaders.SET_COOKIE, RefreshCookies.clear().toString()).build();
	}
```
